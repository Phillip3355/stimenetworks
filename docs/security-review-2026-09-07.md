# 보안 점검 및 구조 정리 — 2026-09-07

저장소의 페이지·컴포넌트, 인증 콜백, 데이터 요청, 서버 API, SQL과 의존성을
점검하고 수정했습니다. 기존 디자인과 주요 기능을 유지했습니다.
운영 DB·배포 설정·실제 사용자 세션은 접속하지 않았으며 침해 여부를 판단하는
포렌식 조사는 아닙니다.

## 발견과 수정

| 문제 | 변경 |
| --- | --- |
| reports RLS 비활성화로 일반 사용자의 보고서 조작 가능 | 공개 조회만 허용, 쓰기는 확인된 관리자만 허용 |
| 메시지 sender 미검사로 관리자 사칭 가능 | 발신자와 문의 소유권을 DB에서 검사 |
| 문의 전체 열 UPDATE로 시각·알림 상태 변경 가능 | 수정 가능한 열과 상태 제한, 삭제는 관리자만 허용 |
| 알림 API의 소유권 검사 누락 | 검증된 토큰 또는 해당 비회원 코드 확인 후 처리 |
| Telegram RPC의 직접 실행 권한 잔존 | PUBLIC, anon, authenticated의 실행 권한 모두 회수 |
| 관리자 판정이 JWT·프론트 목록에 혼재 | auth.users의 현재 인증된 이메일과 DB 목록으로 통일 |
| 회원 문의 제한이 프론트에만 존재 | DB에서 최근 1시간 3개 제한 및 첫 메시지와 원자적 저장 |
| 입력 상한·명령어 문자 검증 부족 | DB와 공통 검증으로 닉네임·본문·메시지·경로 제한 |
| 비회원 RPC가 IP·알림 내부 열까지 반환 | 화면에 필요한 열만 반환 |
| 클라이언트·서버 코드 혼재 | client/server/shared/database 분리, 모듈 경계 표시 |
| 계정 전환 중 이전 비동기 요청 결과 잔존 | 인증 순서 검사와 해제된 조회 결과 무시 |
| 비활성 STAGE UI·운영 DB 시험 스크립트 | 사용하지 않는 코드와 라이브러리 제거 |
| 알려진 의존성 취약점 11개 | Next 16.3.4, React 19.2.8과 관련 의존성 갱신 |

MIME sniffing, iframe 삽입, 외부 base/object 삽입을 제한하는 헤더를 추가했습니다.
ReactMarkdown 기본 HTML·URL 안전 처리를 유지합니다. 현재 CSP는 Next.js와
호환되는 제한 정책이며 엄격한 script-src/nonce 정책까지 완성한 것은 아닙니다.

프레임워크 버전은 [Next.js 공식 보안 공지](https://nextjs.org/blog/august-2026-security-release)와
npm audit 결과를 확인했습니다. DB 권한에는 [Supabase RLS 문서](https://supabase.com/docs/guides/database/postgres/row-level-security)의
테이블 권한과 행 정책을 함께 적용하는 원칙을 따릅니다.

## 기능과 데이터 유지

- 문의·첫 메시지 저장, 메시지·문의 상태 갱신을 각각 같은 트랜잭션으로 처리합니다.
- 회원 문의는 최근 1시간 3개, 비회원 문의는 요청 주체당 최근 1시간 3개입니다.
- 사용자 메시지는 문의별 최근 10분 30개입니다. 고정 시간 경계에서 초기화되지 않습니다.
- 가입 신청은 요청 주체당 최근 1시간 5개이며 동일 플레이어 중복 제한도 유지합니다.
- 기존 행을 삭제하지 않습니다. 비정상 기존 닉네임은 관리자 화면에 표시하되
  명령어 복사를 막습니다. 새 제약은 기존 행을 이후 변경할 때도 적용됩니다.
- 실시간 publication을 삭제하지 않고 필요한 테이블만 추가합니다.
- 알림 전송 실패는 저장된 문의를 취소하지 않으며 기존 claim 중복 방지와
  전송 실패 시 재시도 가능한 해제 흐름을 유지합니다.

## 검증

PGlite의 실제 Postgres 엔진에서 수정 전 보고서 조작, 관리자 사칭, 알림 열 변경,
미인증 관리자 승인, 과대 메시지와 명령어 삽입을 재현했습니다. 수정 후 같은 요청
거부와 정상 회원·비회원·관리자 흐름을 검증했습니다. Supabase처럼 함수에 직접
기본 권한을 부여하는 환경도 재현하고, SQL 재실행 시 데이터 보존을 확인합니다.

API 테스트는 만료·다른 사용자의 토큰, 잘못된 비회원 코드, 타인의 문의와 메시지,
관리자 답장에 대한 사용자 알림, 교차 출처, 과대 JSON과 경로 검증을 포함합니다.
전체 테스트, ESLint, 환경 파일 없는 배포 빌드와 TypeScript 검사, npm audit를 실행합니다.

실제 Google OAuth, Supabase Realtime 네트워크와 운영 텔레그램 수신은 외부 서비스
설정이 필요하므로 로컬 검증과 구분해야 합니다.

최종 확인(2026-09-08): 테스트 81개 통과, ESLint 오류·경고 없음,
npm audit 알려진 취약점 0개, 격리된 배포 빌드·TypeScript 검사 통과.
로컬 배포 서버에서 페이지 10개의 HTTP 응답과 보안 헤더, API 거부 요청 5개,
브라우저 번들에 서버 비밀키 변수·텔레그램 전송 코드가 없는 것도 확인했습니다.
현재 파일 100개의 패턴 검사에서는 발견 없음, Git 이력의 검사 대상 blob 263개에서는
아래 Telegram 토큰 형식의 값 1개가 발견됐습니다.

## 비밀키 검사 및 운영 확인

현재 소스에는 알려진 비밀키 패턴이 없었으나, **Git 과거 이력의 `.env.example`
7행에서 Telegram 봇 토큰 형식의 값 1개를 발견했습니다**(blob `cbcc73f34b82`).
실제로 발급된 토큰이라면 BotFather에서 폐기·재발급한 뒤 배포 환경의
`TELEGRAM_BOT_TOKEN`을 갱신해야 합니다. 현재 파일에서 사라졌어도 과거 이력의
키가 무효화되는 것은 아닙니다. 토큰 유효성 확인이나 외부 봇 호출은 하지 않았습니다.
기존 복제본에 영향을 주는 Git 이력 강제 재작성도 하지 않았습니다.
검사기는 발견해도 파일·위치·종류만 출력합니다. `.env.local`을 포함한 실제 환경
파일은 읽거나 변경하지 않았습니다. `.env.example`은 공개 템플릿으로 별도 검사합니다.
패턴 검사가 모든 형태의 비밀을 보장하지는 않습니다. 배포 환경의 키 값, 과거
배포 번들, 플랫폼 로그는 검사 범위에 포함되지 않습니다.

공개 설정에 service_role JWT 또는 secret 키를 넣으면 빌드를 중단합니다.
정상 anon/publishable 키는 브라우저 공개가 전제된 키이며 DB RLS가 보호 경계입니다.

SQL 준비와 운영 DB 적용은 별개입니다. README의 적용 순서를 따르세요.
다음 사항은 실제 운영 환경에서 추가 확인이 필요합니다.

- 저장소에 없는 추가 DB 테이블·뷰·Storage 정책과 다른 프로젝트의 RPC 사용
- Google OAuth 허용 URL, 이메일 인증 설정
- 비회원 제한의 x-forwarded-for를 Supabase 앞단이 덮어쓰는지 여부.
  신뢰를 확인하기 전에는 완전한 봇·분산 공격 방어로 간주하면 안 됩니다.
- 호스팅 방화벽 요청 제한, HTTPS와 캐시 설정
- 실제 서버 키의 유출·교체 필요 여부

운영 접속 없이 비밀키 교체, SQL 실행 또는 배포를 수행하지 않았습니다.
